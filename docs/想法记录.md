# 捐款系统设计方案 - 聊天记录总结

**讨论时间:** 2026-01-27  
**目的:** 设计基于区块链的透明捐款系统，包含捐款上链、审核、拨款等完整流程

---

## 📌 核心设计决策

### 1. 银行是否需要成为 Fabric Org？

#### ❌ 结论：不需要

**原因：**
- 银行只是系统中的虚拟角色，不是真实机构
- 通过 Spring Security 角色权限控制即可（USER, BANK, ADMIN）
- 链码记录操作人信息，可追溯性足够
- 实现简单，适合 FYP 时间限制

**如果需要更高可信度：**
- 方案2: 可验证凭证（银行签名 + 公钥验证）
- 方案3: 银行 API 集成（双重验证）
- 方案4: 银行作为独立 Org（企业级应用）

**报告中说明：**
> "本项目采用角色权限控制模拟银行参与，所有操作记录在区块链上。在生产环境中，银行可以作为独立 Org 部署节点，提供更高的安全性和不可抵赖性。"

## 🔄 三阶段捐款流程设计

### 阶段 1: 用户捐款 (PENDING)

```
用户 → 发起捐款 → 系统上链 → 状态: PENDING
                              ↓
                        等待银行确认
```

**链码实现：**
```go
type Donation struct {
    DonationID       string  `json:"donationId"`
    CampaignID       string  `json:"campaignId"`
    Amount           float64 `json:"amount"`
    Donor            string  `json:"donor"`
    DonatedAt        string  `json:"donatedAt"`
    PaymentStatus    string  `json:"paymentStatus"`    // PENDING
    CertificateId    string  `json:"certificateId"`    // 区块链证书ID
    EscrowAccount    string  `json:"escrowAccount"`    // 托管账户
}
```

**功能：**
- 用户发起捐款
- 自动生成证书ID: `BC_` + 捐款ID
- 状态设为 PENDING
- 项目的 PendingAmount 增加

---

### 阶段 2: 银行确认收款 (PAID)

```
银行用户 → 查看待确认列表 → 确认收款 → 状态: PAID
                                        ↓
                                  更新项目金额
```

**链码实现：**
```go
type Donation struct {
    // ... 基本信息
    PaymentStatus    string  `json:"paymentStatus"`    // PAID
    
    // 银行确认信息
    ConfirmedBy      string  `json:"confirmedBy"`      // 银行用户email
    ConfirmedAt      string  `json:"confirmedAt"`      // 确认时间
    ConfirmComment   string  `json:"confirmComment"`   // 确认备注
}

// ConfirmPayment - 银行确认收款
func (s *SmartContract) ConfirmPayment(
    ctx contractapi.TransactionContextInterface,
    donationID string,
    confirmedBy string,
    confirmedAt string,
    comment string,
) error
```

**功能：**
- 仅 BANK 角色可操作
- 更新捐款状态为 PAID
- 项目统计：PendingAmount → CurrentAmount
- 检查是否达到拨款条件

---

### 阶段 3: 银行拨款 (RELEASED)

```
银行用户 → 检查项目条件 → 满足条件 → 拨款 → 状态: RELEASED
```

**链码实现：**
```go
type Donation struct {
    // ... 基本信息
    PaymentStatus    string  `json:"paymentStatus"`    // RELEASED
    
    // 拨款信息
    ReleasedBy       string  `json:"releasedBy"`       // 拨款人
    ReleasedAt       string  `json:"releasedAt"`       // 拨款时间
    ReleaseComment   string  `json:"releaseComment"`   // 拨款备注
}

// ReleaseFunds - 银行拨款
func (s *SmartContract) ReleaseFunds(
    ctx contractapi.TransactionContextInterface,
    donationID string,
    releasedBy string,
    releasedAt string,
    comment string,
) error
```

**拨款条件示例：**
- 达到目标金额的 80%
- 项目状态为 IN_PROGRESS
- 所有捐款都已确认（PAID）

## 🔐 信任模型设计

### 问题：用户如何信任银行确认？

在没有银行独立背书的情况下，存在平台可能伪造银行操作的风险。

### 解决方案对比

| 方案 | 信任模型 | 实现难度 | 可信度 | 推荐场景 |
|-----|---------|---------|-------|---------|
| **方案1: 完全信任后端** | 中心化信任 | ⭐ 简单 | ⭐⭐ | FYP演示 |
| **方案2: 可验证凭证** | 密码学验证 | ⭐⭐⭐ | ⭐⭐⭐⭐ | 中型项目 |
| **方案3: 银行API集成** | 第三方验证 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 实际项目 |
| **方案4: 银行作为Org** | 多方背书 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 企业级 |

### 推荐实现（FYP）

**方案1 + 方案2的概念**

## 🔐 公钥私钥体系

### 核心概念

```
私钥 (Private Key)：
- 只有机构自己知道
- 用于签名（证明是我）
- 绝对保密

公钥 (Public Key)：
- 可以公开给所有人
- 用于验证签名（验证是不是他）
- 可以随便分享
```

### 应用场景

#### 场景1: 银行确认收款

```
1. 银行用私钥签名
   ├── 原始数据: donationId + amount + timestamp
   └── 生成签名: signature

2. 签名上链
   ├── 原始数据
   ├── 签名
   └── 银行公钥

3. 任何人验证
   └── 用公钥验证签名 → ✅ 真实 / ❌ 伪造
```

#### 场景2: 防伪追责

```
如果捐款出问题：
1. 查询区块链记录
2. 获取签名和公钥
3. 验证签名 → 确认操作者
4. 有证据追责
```

### 实现示例

```java
// 银行确认时签名
public void confirmPayment(String donationId, BigDecimal amount) {
    // 1. 构造数据
    String data = donationId + amount + timestamp;
    
    // 2. 用私钥签名
    String signature = signWithPrivateKey(data, bankPrivateKey);
    
    // 3. 上链存储
    blockchain.confirmPayment(donationId, data, signature, bankPublicKey);
}

// 用户验证
public boolean verifyPayment(String donationId) {
    // 1. 从链上获取
    BlockchainData bc = blockchain.getDonation(donationId);
    
    // 2. 用公钥验证
    return verifyWithPublicKey(bc.data, bc.signature, bc.publicKey);
}
```

## ✅ 实现完成：捐款显示名功能 (2026-01-27)

### 已实现功能

用户可以选择三种捐款显示方式：

1. **默认显示名（default）**
   - 使用用户自己的 displayName
   - 公开显示在捐款列表中

2. **自定义显示名（custom）**
   - 用户可以输入任意显示名称
   - 最多 50 个字符
   - 临时性显示，每次捐款可以不同

3. **匿名捐款（anonymous）**
   - 显示为"匿名"
   - 不暴露任何身份信息

### 数据存储策略

**链上（Blockchain）:**
- `donor`: 真实用户标识（email）- 保留在链上用于追溯
- `displayName`: 公开显示名称（用户选择或自定义）
- `isAnonymous`: 是否匿名标记

**链下（Database）:**
- `user_id`: 外键关联到真实用户（始终保留）
- `display_name`: 公开显示名称
- `is_anonymous`: 是否匿名
